# Ревью C#/.NET backend

Проверять изменения с учетом контрактов, архитектуры и правил конкретного репозитория. Локальные соглашения не являются требованиями ко всем C#-проектам.

## Область работы

- Сначала определить режим: независимое ревью или исправление замечаний. Ревью само по себе не разрешает менять код.
- Прочитать инструкции репозитория, спецификацию и соседние реализации. Определить целевую ветку и посмотреть полный production diff, затем затронутые тесты и прямые зависимости.
- При повторном ревью определить изменения после предыдущего проверенного commit. Старый APPROVE не является доказательством для нового diff.
- Замечание ревьювера оценивать технически: какой контракт, инвариант или локальное правило нарушено. Вопрос «не рассматривал ли вариант» не считать требованием переписать реализацию.
- Исправлять минимально. Не добавлять сервисы, интерфейсы и рефакторинг за пределами задачи ради формального SOLID или уменьшения числа строк.

## Структура и читаемость

- Следовать разделению query, handler, validator, моделей и DTO, принятому в проекте. Если там один именованный тип на файл, не объединять новые records или EF-модели в большой файл; связанные типы группировать в папку по назначению.
- Упрощать глубокую вложенность guard clauses и небольшими методами, когда это раскрывает смысл. Не дробить линейный алгоритм на однострочные прокси.
- Использовать доменные enum для уже определенных бизнес-состояний. Лимиты, количества и таймауты оформлять осмысленными константами или настройками, не enum.
- При наличии общего Messages размещать новые строки исключений, логов и ошибок конфигурации в нем. Не создавать зависимость общего слоя от Messages конкретного адаптера. Не обещать локализацию только из-за появления констант.
- Комментарии оставлять для неочевидных инвариантов, совместимости и причин оптимизации. Убирать пересказ кода и дубли. Язык комментариев брать из правил проекта.

## Границы адаптеров и API

- Общий контракт должен описывать потребность потребителя, а не внутреннее устройство конкретного источника. Не выносить parser/resolver в публичные абстракции только для удобства общего валидатора, если его внутренние части существуют лишь у одного адаптера.
- Общая валидация проверяет общие ограничения. Формат непрозрачного идентификатора разбирает владеющий им адаптер и сообщает о некорректном вводе способом, который API преобразует в требуемый ответ.
- Для идентификаторов разных внешних систем рассмотреть string на общей границе: другой адаптер может использовать Guid. Не переводить все доменные числовые ID в строки автоматически.
- Смена типа ID в DTO является изменением wire-контракта. Проверить OpenAPI, реальные проверки фронта и построение ссылок, а не только компиляцию backend. Не допускать потери точности long в JavaScript. Адаптацию и порядок выпуска клиентов указать явно.
- Для произвольных дополнительных данных разных адаптеров рассмотреть нейтральную Metadata со словарем, если фиксированные поля протаскивают специфику источника. Общий слой не должен знать про UI-ссылки. Не заменять словарями стабильные, осмысленные поля контракта без причины.
- При словаре string/string определить формат дат и ID, отсутствие ключа и пустое значение; не считать порядок вставки ключей частью контракта. Порядок задач проверять отдельно, если он значим.

## Контроллеры, mapping и ошибки

- Контроллер отвечает за HTTP-вход и делегирование. Применять существующий mapper проекта; в проекте с Mapperly не добавлять параллельный ручной mapping без причины.
- Проверить результат mapping на уровне HTTP: имена полей, строковые ID, metadata, nullable и отсутствующие значения.
- ProducesResponseType оформлять согласованно с соседними ручками и реальными ответами. Вопрос о генерации документации не является поводом добавлять новую инфраструктуру в маленький MR.
- Ошибка источника должна возникать или переводиться в контрактное исключение на границе источника, а не маскироваться контроллером. Объявлять исключение в слое, который владеет этим контрактом; не переносить его между слоями механически.
- Не превращать отказ в доступе, ошибку ввода и отмену клиентом в «источник недоступен». Проверять реальный middleware и HTTP-ответы, включая поведение при занятом gate.
- Проверку принадлежности роли сохранить до чтения данных. Перенос parser внутрь адаптера не разрешает удалить контроль доступа.

## DI, EF Core и транзакции

- Сохранять структуру DI проекта: верхний extension собирает уровни интеграции; каждый уровень регистрирует свои детали. Публичные реализации и общие утилиты размещать в соответствующих существующих методах. Настройки и их валидацию группировать с конфигурацией.
- Reader может зависеть от внутреннего интерфейса контекста с минимально необходимым API. Не переносить весь DbContext в интерфейс без потребности.
- Внутренний интерфейс reader оправдан, если потребителю нужна подмена чтения в тестах. Не делать его публичным и не добавлять интерфейс каждому классу автоматически.
- При keyed DI интерфейс контекста должен получать тот же scoped экземпляр, на котором потребитель открывает транзакцию. Регистрация второго DbContext может незаметно вынести чтение за границу снимка. Проверить общий экземпляр тестом DI.
- Сохранить lifetimes, выбор primary/replica, isolation level, READ ONLY, границы commit, отмену и освобождение ресурсов. Подмена зависимости интерфейсом не должна менять запросы и transaction ownership.
- EF read-модели не обязаны быть доменной моделью источника. Оценивать используемые поля и связи по запросам. Большое число классов само по себе не доказывает необходимость сырого SQL.
- EF и сырой SQL сравнивать по сложности, составу результата, параметризации, планам и сопровождению. Не переписывать проверенный reader ради сокращения числа файлов. Если сравнения не было, сказать об этом прямо.

## Проверки без смены поведения

- Для исправления ошибки по возможности сначала воспроизвести ее тестом. Для валидации проверять HTTP, не только validator.
- При переносе DI проверить разрешение сервисов и общий контекст. При замене ID проверить обычные строки, большие числовые значения и Guid там, где контракт их допускает.
- Оптимизацию reader проверять сравнением полных результатов, а не счетчиков: пустая выборка, границы порога, fallback, пересечения популяций и отсутствие собственного этапа. Включать независимые категории задач, которые предварительный отбор может потерять.
- Для календарной логики использовать согласованную бизнес-таймзону и граничные даты, а не локальную дату машины. Повторные события и разные подразделения проверять по спецификации.
- Порог, лимит gate и таймаут брать из текущего контракта/настроек. Не переносить числовые значения и решения об ограничении нагрузки из другого проекта без обоснования.
- Запускать релевантные тесты, затем доступные backend-тесты и Release build. Для PostgreSQL-тестов сообщать, действительно ли они выполнились или были пропущены. Использовать разрешенную тестовую БД.
- Применять dotnet format только к измененным файлам и проверять git diff --check. При обещании неизменности SQL опираться на diff запросов и, когда изменения затрагивают EF translation, сравнение SQL/параметров или интеграционные проверки.
- Проверить полный diff на локальную авторизацию, mocks и посторонние настройки. Локальную работу сохранять отдельно от production MR.

## Результат и общение с ревьювером

Короткий отчет: подтвержденные проблемы с файлами, выполненные проверки и ограничения. Если запрошен вердикт, выбрать READY, READY WITH NOTES или NOT READY и разделить блокеры code review, условия production merge и необязательные улучшения. Не выдавать неизвестную конфигурацию QA или production за дефект кода.

Ответы в тредах писать просто: что поменял и, если нужно, зачем. Например: «Да, поменял на IExternalDbContext. Контекст остался общим с provider, добавил тест на это». Для неподтвержденной альтернативы: «Вариант с сырым SQL пока не сравнивал. Здесь оставил EF, чтобы не переписывать проверенные запросы».

Навык сам не дает разрешения на commit, push или публикацию ответов. Действовать в пределах запроса пользователя. При разрешенной публикации отвечать в исходных тредах, не дублировать одинаковые сообщения; при просьбе упростить ответ редактировать существующий. Не резолвить треды без отдельного указания пользователя.
